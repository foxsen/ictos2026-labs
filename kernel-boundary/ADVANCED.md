# 进阶：共享内存传数据，同步机制传通知

## 1. 任务与边界

实现两个 Linux 进程间的同步请求—回复：客户每次发一个请求，服务完整接收后原样回复，客户收到匹配回复才开始下一次。数据放在共享内存中；用可阻塞的进程间同步机制通知对方。建议使用 futex，也可使用进程共享信号量或条件变量，但必须说明选择及其开销。只有轮询的实现不满足核心要求；混合自旋可作为完成阻塞版本后的附加优化。

四种有效载荷长度为 1、64、1024、4096 字节。框架统一添加 8 字节序号，因此传输长度分别为 9、72、1032、4104 字节。socket 和共享内存都使用相同的报文、服务逻辑和测量程序，避免通过减少工作取得表面优势。

需自行完成 `linux/src/advanced/transport_shm.c` 的 `request()`、`receive()`、`reply()`。共享映射的分配和清理由骨架提供，可以调整布局，但保持 `transport.h` 的接口。不得调用 socket 代替共享内存数据传输，不得直接在客户中伪造服务回复。

## 2. 提供什么，完成什么

| 已提供 | 学生完成 |
|---|---|
| transport 接口、共享区分配与生命周期 | 状态含义、缓冲区所有权及复用规则 |
| socket 完整对照 | 请求发布、等待、唤醒和回复协议 |
| fork、进程绑核、批量计时 | 原子操作 / 同步原语与内存顺序 |
| 序号 / 内容校验、超时终止 | 正确处理竞争、提前通知、重复唤醒和系统调用中断 |
| 参数矩阵、CSV 汇总、环境与源码快照 | 解释测量差异，评价适用条件 |

骨架中的两个原子状态字和两个缓冲区只是建议布局，不是已经实现的协议。三个通信函数有意返回 `ENOSYS`，未完成时测量必须失败。

## 3. 实现前写一页协议说明

至少列出以下内容，并随着实现修正：

1. 每个状态的含义；客户、服务分别能够修改哪些字段。
2. 请求数据何时可读；客户何时可覆盖请求缓冲区；回复缓冲区同样说明。
3. 以怎样的原子操作或锁保证先完成数据写入、再让对方看到就绪状态。不要把 `volatile` 当作同步。
4. 当通知先于对方等待发生时，如何保证请求不会丢失；等待返回后如何重新判断条件。
5. 调用失败时如何向框架返回 `-1` 和 errno。框架负责超时后清理进程，不要求本次实现崩溃后的透明恢复。

futex 资料入口：[futex(2)](https://man7.org/linux/man-pages/man2/futex.2.html)、[FUTEX_WAIT](https://man7.org/linux/man-pages/man2/FUTEX_WAIT.2const.html)。注意 futex 字的大小与对齐、跨进程时的共享属性，以及 `EAGAIN` / `EINTR` 的处理。通知与内存可见性是相关但不同的责任；通过同步或 C 原子内存序建立需要的可见性关系。不要直接采用 `_PRIVATE` 形式处理两个进程。

## 4. 编译与正确性检查

所有命令在 `labs/kernel-boundary/` 执行：

```bash
make -C linux advanced
python3 scripts/run-advanced.py --mode check --transport socket
# 修改 transport_shm.c 后：
python3 scripts/run-advanced.py --mode check
```

默认检查两种布局、四种长度、三个 seed；每个配置 5000 次正式往返和 50 次预热。客户和服务都检查单调递增序号以及随序号改变的全部有效载荷，并在若干位置主动让出 CPU，以增加交错执行机会。错误序号、错误内容、传输错误、进程异常退出或超时均判失败。

框架提供的 `make -C linux test` 只验证测量工具本身；不能替代上面的学生实现检查。未完成骨架时，`shm` 报 `STUDENT TODO` 属正常现象。

可以指定两个当前允许使用的 CPU：

```bash
python3 scripts/run-advanced.py --mode check --client-cpu 2 --server-cpu 3
```

这里 2、3 仅为示例，应从 `os.sched_getaffinity(0)` 或 `environment.txt` 选择实际允许的 CPU。默认客户端为第一个允许的 CPU，“different”服务端为另一个；“same”布局中双方都在客户端 CPU。不同逻辑 CPU 可能仍是 SMT 兄弟，报告应根据 `lscpu` 记录是否同物理核、同 LLC、同 NUMA 节点。

仅一个可用 CPU 时加 `--placements same`，保留限制说明；在可用的双 CPU 环境补做异核对照。`--timeout` 是每个子运行的上限，默认 30 秒；正常程序若因慢机器超时，可增大并记录理由，不以无限等待绕过死锁。

## 5. 测量与产物

通过检查后运行：

```bash
python3 scripts/run-advanced.py --mode bench
```

该命令仍会先跑完整正确性检查，再依次运行两种传输、两种 CPU 布局、四种长度。计时默认每组 51 批、每批 1000 次，预热 50 次。

- 检查运行逐次改变并校验数据，主动调度扰动不进入性能计时。
- 计时运行使用固定有效载荷，每次更新序号；服务原样回复。每批结束后校验最终回复，校验耗时不计入该批时间。
- 报告为整批时间 / 往返数，包含共同循环与传输开销；无基线相减。
- 两种实现均使用进程私有的调用方缓冲区；共享内存中仍可能有用户态复制，不预设“零复制”。

默认每次创建新的结果目录，也可用 `--output results/my-advanced-01` 指定一个**尚不存在**的目录。输出包括：

| 文件 | 用途 |
|---|---|
| `check-*.stdout.txt` / `*.stderr.txt` | 全部正确性记录和失败原因 |
| `bench-*.csv` / `*.stderr.txt` | 各配置原始批次均值及运行参数 |
| `summary.csv` | 每组 median、mean、P95，单位 ns/往返 |
| `comparison.csv` | 相同布局 / 长度的 SHM−socket 差值及 SHM/socket 比值 |
| `environment.txt`、`run.json` | CPU、参数、逐次命令、退出状态、二进制 / 源码哈希 |
| `source/` | 本次实际使用的传输源码和测量工具快照 |

任何配置失败都保留日志，`run.json` 标记失败，不输出整套性能汇总。不要把未完成的部分输出用于最终排名。

若使用 pthread 等原语需要额外链接选项，记录编译命令，例如先 `make -C linux clean`，再以 `LDFLAGS=-pthread python3 scripts/run-advanced.py --mode check` 重新构建。改变编译选项时必须主动重建。

## 6. 报告与评价

1. 提交实现和一页协议说明；标出一次请求—回复经过的状态变化、等待点和复制位置。
2. 画两张消息长度曲线：同核一张、异核一张，每张同时展示 socket 和共享内存。标注 median ns/往返，并列出 P95 与采样数。
3. 引用 `comparison.csv`，对比四种长度、两种布局的差值及比值。若不能完成异核部分，解释环境限制，不编造结果。
4. 结合代码说明减少或增加的成本：内核数据复制、用户态复制、系统调用、唤醒 / 调度、跨核通信。无法从当前测量独立分离的项标明为推测。
5. 若要统计 futex 调用次数等路径信息，另跑一次跟踪实验，不把被跟踪的延迟混入正式性能表。
6. 联系一条课程论文论断：例如大消息经共享内存传递的理由。讨论自己的实现在哪些条件下支持这一思路，哪些条件仍未覆盖。不要求共享内存一定更快。

框架按固定次序串行测量；机器有频率漂移或后台扰动时，应重复完整运行、保留各次结果，并检查结论是否稳定。基础 L2 没有序号头，不能与这里的 SHM 直接比较。

## 7. 验收重点

正确性和公平性先于性能。除了运行检查，教师还会检查缓冲区复用与内存顺序的解释，并可能改变 seed、非标准长度或 CPU 配置。一次测试通过不等于证明所有交错都正确。共享内存方案较慢、收益只出现在某些长度，都可以构成完整的实验结论。
